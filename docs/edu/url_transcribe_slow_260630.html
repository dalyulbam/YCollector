URL 전사는 왜 느린가 — 추출·비공개 영상·진행률

"재생목록 URL 전사가 유독 오래 걸린다. 다운로드가 느린 건가?"에 대한 측정 기반 설명. 핵심: 느린 건 다운로드 속도가 아니라 ① 영상마다의 YouTube 추출(~16초)과 ② 비공개 영상을 인증 없이 건너뛰는 낭비다. 진행바를 어떻게 보이게 했는지도 함께 다룬다.

바로가기 · ① 파이프라인 · ② 진짜 병목: 추출 · ③ 비공개 영상 · 접근 권한 · ④ "다운로드 하나"보다 느린 이유 · ⑤ 진행률 가시화 · ⑥ 실측 근거 · ⑦ 더 빠르게

1. URL 전사 파이프라인 한눈에

URL(재생목록) ─▶ [_download_collect] 재생목록 "전체"를 먼저 다운로드 │ (영상마다: 추출 → 다운로드 → 병합) ▼ [_run_analyze] 받은 파일들을 그 다음 "전부" 전사 │ (Whisper: 파일마다 0→100%) ▼ _analysis/*.script.md (+ .summary.md)

핵심 성질 두 가지:

  • 다운로드-전부 → 전사-전부 순서다(인터리빙 아님). 그래서 재생목록이 다 받아질 때까지 전사 산출물(_analysis)이 하나도 안 보인다.
  • 다운로드는 yt-dlp가 재생목록 항목을 한 개씩 순차로 처리한다.

2. 진짜 병목 — 영상마다의 "추출" 단계

바이트(영상 데이터)가 흐르기 전에, yt-dlp는 영상 1개마다 아래를 한다. 실측 약 16초(다운로드 0바이트 기준):

[youtube] Downloading webpage ← 영상 페이지 [youtube] Downloading android vr player API JSON ← 포맷 메타(innertube API) [youtube] Downloading player 7a37f05b-main ← player.js (서명 함수 들어있음) [youtube] [jsc:deno] Solving JS challenges using deno ← n-sig(JS 챌린지) 풀이! [youtube] Downloading m3u8 information ← 스트림 목록 [info] Downloading 1 format(s): 136+251 ← 여기서야 다운로드 시작

가장 무거운 건 n-sig 풀이다. YouTube는 스트림 URL에 자바스크립트로 변형된 서명을 요구하는데, yt-dlp가 deno(JS 런타임) 서브프로세스를 띄워 그 챌린지를 푼다. 이게 네트워크 왕복 + 로컬 CPU 모두를 쓴다.

즉 이 16초는 "느린 인터넷"이 아니라 YouTube 접근 + JS 챌린지 해석에 드는 고정 비용이다. 영상 1개면 한 번만 내지만, 재생목록 N개면 N번 낸다.

3. 비공개 영상 & 접근 권한 핵심

이번 재생목록을 실제로 조사하니 총 120개인데 다수가 Private video였다:

ERROR: [youtube] oz1aC5Hjp0w: Private video. Sign in if you've been granted
  access to this video. Use --cookies-from-browser or --cookies ...
  • 비공개 영상은 로그인(쿠키) 없이는 접근 불가. yt-dlp는 --ignore-errors 덕에 그런 항목을 건너뛴다 → 공개분만 받힌다(예: 120개 중 31개).
  • 그런데 건너뛰기 전에도 추출은 시도한다 → 비공개 1개마다 십수 초 쓰고 산출물 0. 이게 "대기"를 크게 늘린다.
  • "내 개인 채널 영상인데 왜?" → 비공개/멤버십/연령제한 영상은 그 채널 소유 계정으로 로그인해야 도구가 접근한다.

권한 주는 법 — 로그인 쿠키

방법명령 / 설정메모
권장 A. ycollector-login uv pip install "playwright>=1.50.0" --native-tls
uv run --no-sync playwright install chromium
uv run --no-sync ycollector-login		 별도 Chromium 창에서 본인 계정 로그인 → %APPDATA%\YCollector\cookies.txt 자동 저장. 메인 Chrome 안 닫아도 됨. 서버/CLI가 자동 사용

4. "다운로드 하나"보다 느리게 느껴지는 이유

요인설명
개수다운로드 패널은 보통 영상 1개, URL 전사 '전체'는 재생목록 N개(여기선 120). per-영상 추출 16초 × N.
비공개 낭비비공개 항목도 추출 시도 후 스킵 → 시간만 쓰고 산출 0.
풀영상 바이트전사엔 오디오만 필요한데 기본은 1080p 영상 + 병합 + 자막을 받는다(영상 1개 100~300MB vs 오디오 5~15MB).
진행바 정지(과거)예전엔 다운로드 중 진행바를 안 움직여 "멈춤"처럼 보였다 → §5에서 수정.
중요: per-byte 다운로드 속도는 다운로드 패널과 동일하다(같은 yt-dlp, 같은 옵션). 길어지는 건 "받는 양 × 개수 + 추출/비공개 오버헤드"지 속도 저하가 아니다.

5. 진행률을 보이게 한 방법

"다운로드도 몇 %인지 알려줘야지"에 대한 구현. 이제 다운로드 단계도 진행바가 움직인다.

추출 중 8/120 · 제목… ← on_meta: 재생목록 위치로 바 갱신(느린 추출 구간 가시화) 다운로드 8/120 · 73% (7개 완료) ← on_progress: (완료수 + 현재파일%) / 전체 ───────────────────────────────── 다운로드 완료 → 진행바 0 리셋, 상태 '전사'로 전환 → 전사 0→100%
레이어변경
engine/ytdlp.py MetaInfo에 playlist_index/playlist_count 추가, _META_TEMPLATE에 %(playlist_index)s·%(playlist_count,n_entries)s 추가, _parse_meta 6필드 파싱
server.py _download_collect _bar() 헬퍼: 재생목록이면 (i-1+파일%)/N, 단일이면 파일%. 단조 증가 보장(거꾸로 안 튐). on_meta/on_progress/on_file 가 job.progress emit
server.py _run_url_analyze 다운로드→전사 전환 시 progress=0, status="transcribing" 로 리셋(단계 구분)

웹은 SSE progress 이벤트의 progress(바)·status(상태)·speed/eta/message(텍스트)를 그대로 그린다(webui/app.js trackJob).

6. 실측 근거

측정결과
단일 영상 추출(다운로드 0바이트)~16초 (webpage→API→player.js→deno n-sig→m3u8)
재생목록 총 개수cnt=120 (실측, 공개 항목의 playlist_count)
비공개 항목1~7번 등 다수 Private video 에러 → 스킵
진행률 필드 채워짐YCMETA idx=08 cnt=120 (공개 영상에서 index/count 정상)
이미 받은 공개분download2read/Orang_fantasy 31개(~4.1GB)

7. 더 빠르게 하려면

  • 쿠키 설정(§3) — 비공개 접근. "헛도는 16초"가 실제 산출로 바뀐다. 본인 채널이면 필수.
  • 오디오 전용 다운로드(앨범 OFF일 때) — bestaudio/best로 받으면 10~20배↓. 전사엔 오디오면 충분(단 장면 앨범은 영상 필요 → 조건 분기).
  • 범위 제한 — [playlist] items = 1-10 또는 max_downloads 로 일부만.
  • yt-dlp 최신 — uv pip install -U yt-dlp --native-tls. 구버전은 YouTube 변경에 취약하고 추출이 더 자주 깨진다.
  • (설계) 다운로드↔전사 인터리빙 — 1개 받자마자 전사(GPU) 시작하면 첫 결과가 빨리 나오고 I/O와 연산이 겹친다.
