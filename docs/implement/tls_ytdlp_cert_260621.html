TLS 가로채기 환경에서 yt-dlp 인증서 검증 실패 수정

재생목록 URL 다운로드가 [unknown] ERROR: Unable to handle request: 2 unexpected error(s) 로 실패하던 문제. 겉보기엔 yt-dlp 네트워킹 에러였지만 실체는 백신/프록시 TLS 가로채기로 인한 SSL 인증서 검증 실패였고, 서버가 쓰던 .venv yt-dlp 가 OS 신뢰 저장소를 안 써서 깨졌다. 검증을 켠 채로 고쳤다.

바로가기 · ① 증상 · ② 원인 추적 · ③ 진짜 원인 · ④ 수정 · ⑤ 변경 파일 · ⑥ 패키지·기술 · ⑦ 검증 · ⑧ 적용 · ⑨ 서버 재실행 takeover

1. 증상

분석 보드/다운로드 패널에서 재생목록 컨텍스트 URL을 받으면 잡이 곧장 실패했다:

DL  https://www.youtube.com/watch?v=N3fgTolQON8&list=PLiB54OIQ9yEIkm6Lt0zbVfxmQq8QP9yTs
id: 4cd02a3e7b10 · 대기 중
[unknown] ERROR: Unable to handle request: 2 unexpected error(s)
  • [unknown] 은 앱의 에러 분류(classify_error)가 알려진 패턴에 못 맞춰 붙인 카테고리.
  • Unable to handle request: 2 unexpected error(s) 은 yt-dlp 네트워킹 계층이 낸 메시지(우리 코드 아님).
  • 혼란 포인트: 콘솔에서 yt-dlp 를 직접 돌리면 잘 됐다.

2. 원인 추적 (추측 금지 · 직접 재현)

① 메시지의 출처

yt_dlp/networking/exceptions.py 의 NoSupportingHandlers 가 범인. yt-dlp 는 HTTP 요청마다 등록된 핸들러(urllib·requests…)를 차례로 시도하는데(networking/common.py RequestDirector.send):

for handler in handlers: handler.validate(request) # 실패 → UnsupportedRequest (예상된 거절) handler.send(request) # 실패(RequestError 아님) → "unexpected error" 로 수집 # + 로그: "[urllib] Unexpected error: …" 모두 실패 → raise NoSupportingHandlers # → "Unable to handle request: N unexpected error(s)"
핵심: 진짜 원인은 [urllib] Unexpected error: … / [requests] Unexpected error: … 줄에 들어있는데, download() 는 stderr 의 마지막 줄만 잡에 표시해서 그 줄이 묻혔다. 그래서 "Unable to handle request" 라는 껍데기만 보였다.

② 숨은 줄을 끄집어내 재현

앱과 같은 플래그로 실제 다운로드를 돌려 가려진 스택을 확인하니 정체가 드러났다:

ssl.SSLCertVerificationError: [SSL: CERTIFICATE_VERIFY_FAILED]
  certificate verify failed: unable to get local issuer certificate (_ssl.c:1032)
yt_dlp.networking.exceptions.CertificateVerifyError: [SSL: CERTIFICATE_VERIFY_FAILED] …
ERROR: [youtube] N3fgTolQON8: Unable to download API page: [SSL: CERTIFICATE_VERIFY_FAILED] …

즉 이 PC의 백신/프록시 TLS 가로채기 문제였다. 가로채는 프록시가 서버 인증서를 자체 CA로 바꿔치는데, 그 CA가 certifi 번들엔 없어서 검증이 깨진다.

③ "콘솔은 되는데 서버는 안 됨" — 서로 다른 yt-dlp

엔진은 shutil.which("yt-dlp") 로 yt-dlp 를 찾는다. uv run 환경에선 .venv\Scripts 가 PATH 앞이라 venv 의 yt-dlp 가 잡힌다 — 내 콘솔의 시스템 yt-dlp 와 다른 바이너리:

실행 맥락실제 yt-dlp 경로버전결과
콘솔 yt-dlp…\Python313\Scripts\yt-dlp2026.06.09✅ 정상
uv run ycollector-server…\.venv\Scripts\yt-dlp.exe2026.03.17❌ SSL 실패

버전 업으로는 안 고쳐졌다 (가설 폐기). venv yt-dlp 를 콘솔과 같은 2026.06.09 로 올려도 여전히 동일 SSL 에러. 같은 버전·같은 Python 3.13.13·같은 OpenSSL 3.0.19·같은 certifi 인데도 한쪽만 깨졌다 → 차이는 yt-dlp 가 아니라 인터프리터 환경에 있었다.

3. 진짜 원인 — venv 엔 OS 신뢰 저장소 훅이 없었다

시스템 Python 의 site-packages 엔 pip_system_certs.pth 가 있었고, venv 엔 없었다. 이 .pth 는 인터프리터 시작 시 Python 의 SSL 을 OS 인증서 저장소(가로채는 프록시 CA가 들어있는 Windows 저장소)에 연결한다. 그래서 시스템 Python 으로 도는 yt-dlp 는 자동으로 통과했고, venv yt-dlp 는 certifi 번들로만 검증해 깨졌다.

요소시스템 Python.venv (서버)
pip_system_certs.pth✅ 있음❌ 없음 → 원인
truststore 설치있음있음 (그러나 미주입)
Python / OpenSSL3.13.13 / 3.0.193.13.13 / 3.0.19 (동일)
certifi 번들가로채기 CA 없음가로채기 CA 없음
왜 truststore 만으론 부족했나: 프로젝트는 in-process HTTPS(anthropic/openai/whisper)에 truststore.inject_into_ssl() 를 쓴다. 그런데 yt-dlp 는 별도 프로세스라 부모에서 주입해도 자식엔 안 닿는다. .pth 훅(pip_system_certs)은 그 자식 인터프리터가 시작할 때 스스로 OS 저장소를 붙이므로 서브프로세스 yt-dlp 까지 커버한다.

막다른 길도 기록 (정직)

ssl.enum_certificates("ROOT"/"CA") 로 Windows 저장소를 PEM(72개)으로 떠 SSL_CERT_FILE 로 물려도 실패했다 — 그 열거 API 엔 가로채기 CA 가 안 잡혔다. 신뢰할 수 있는 길은 CryptoAPI 전체 체인 검증을 쓰는 pip_system_certs/truststore 였다.

7. 검증

  • 재현: venv yt-dlp(2026.03.17/06.09 모두)에서 CERTIFICATE_VERIFY_FAILED 확인. --no-check-certificate 로 통과(exit 0) 확인.
  • 보안 유지 수정: venv 에 pip-system-certs 설치 후 --simulate → VERIFIED-OK(검증 ON, exit 0).
  • E2E(서버 경로): venv Python 으로 YtdlpEngine().download(no_check_certificate=False) 실제 다운로드 → using yt-dlp: .venv\Scripts\yt-dlp.EXE, DOWNLOADED OK.
  • 설정 라운드트립: settings_to_dict/from_dict/load_settings 에 no_check_certificate 반영 확인.
  • 분류: classify_error("Unable to handle request: …") → cert-verify, SSL 메시지도 cert-verify.
  • 스모크: config·engine.ytdlp·server·cli import OK. CLI --help 에 --no-check-certificate 노출.

못 한 것(정직): 프로젝트 자체 테스트는 없음(pytest 수집 0) — import 스모크 + 실다운로드로 대체. ruff 는 dev extra 미설치라 린트 미실행.

무해한 참고: uv run 이 "venv 가 3.13.11 로 생성됐는데 현재 3.13.13" 경고를 낸다. 이번 문제와 무관한 기존 환경 드리프트라 건드리지 않았다.

8. 적용

# 이미 적용됨(venv): pip-system-certs 설치 + uv.lock 기록 + yt-dlp 상향.
# 깨끗한 환경에서 재현/동기화 시:
uv sync --extra web --native-tls          # pip-system-certs 포함 설치

# 서버 재시작 후 실패 잡 재시도
uv run ycollector-server                  # → http://127.0.0.1:8765/
#   큐 패널의 "재시도"(또는 URL 재입력) → 이제 통과

# OS 신뢰 저장소로도 안 되는 환경이라면(최후 수단):
#   %APPDATA%\YCollector\settings.ini 또는 루트 settings.ini 의
#   [network] no_check_certificate = true

9. 서버 재실행 — 기존 인스턴스 자동 교체

문제: uv run ycollector-server 를 다시 실행하면 failed to remove directory .venv\Lib: 액세스가 거부되었습니다 (os error 5). 원인 둘 — ① 떠 있던 서버가 .venv\Lib 의 .pyd/.dll 을 잠가둠, ② pyvenv.cfg(3.13.11) ↔ 시스템 Python(3.13.13) 드리프트로 uv 가 venv 재생성을 시도. 그래서 "닫고 새로 열기" 가 안 됐다.

해결: 서버 시작 시 같은 포트의 기존 YCollector 서버를 닫고 인계

uv run --no-sync ycollector-server # ← --no-sync: venv 재생성 건너뜀(잘린 휠 위험 회피) └─▶ main(): 포트 8765 점유? ──no──▶ 그대로 bind │ yes ▼ GET /api/health 응답이 'YCollector' 인가? ──no──▶ 종료(다른 앱 보호, exit 12) │ yes (우리 서버 확정) ▼ 포트 소유 PID 종료(netstat→pidfile, taskkill /T) ─▶ 포트 해제 대기 ─▶ bind
구성요소변경요약
_replace_existing_instance()NEW 포트가 비었으면 통과. 점유 시 /api/health 로 우리 서버임을 확인한 뒤에만 종료(엉뚱한 앱 보호)
_is_our_server() / _pid_listening_on() / _terminate_pid()NEW health 프로브 · Windows netstat 로 포트 소유 PID · win taskkill /T /F / posix SIGTERM→SIGKILL
server.pidNEW %APPDATA%\YCollector\server.pid 에 PID 기록(다음 실행의 종료 대상 fallback), 정상 종료 시 삭제
--no-replace / --port 0NEW / 기존 --no-replace: 교체 안 함(충돌 시 실패). --port 0: 빈 포트 자동 선택(교체 불필요)
왜 --no-sync 가 필요한가: takeover 는 서버 코드 안에서 돈다. 그런데 그냥 uv run(동기화 모드)은 우리 코드가 실행되기 전에 venv 를 재생성하려다, 기존 서버가 건 락 때문에 거기서 먼저 실패한다. --no-sync 면 재생성을 건너뛰어 main() 이 실행되고 → 기존 서버를 닫고 → 새로 뜬다. 결론: uv run --no-sync ycollector-server 한 줄을 반복 실행하면 항상 "닫고 새로 열기".

검증

  • 서버 A(8765, PID 21976) 기동 → 서버 B 를 8765 로 기동 → A 종료 확인 · B 가 포트 인계 · /api/health HTTP 200.
  • taskkill /T 가 포트 소유(자식)와 함께 uv run 래퍼 트리까지 정리됨을 확인.
  • 안전장치: _is_our_server 가 false 면(다른 앱) 종료하지 않고 exit 12 + 안내. 자기 자신(os.getpid())은 종료 대상에서 제외.
# 반복 재실행 = 자동 교체
uv run --no-sync ycollector-server         # 기존 8765 서버를 닫고 새로 연다
# 기존 인스턴스를 건드리지 않으려면
uv run --no-sync ycollector-server --no-replace
# 빈 포트로 별도 기동
uv run --no-sync ycollector-server --port 0
