대량 다운로드 & 전사 작업 중 발생한 에러 정리

채널 2개의 원본 영상 96개와 쇼츠 2종(목표 1,062개)을 받아 전부 전사하는 작업에서 나온 에러 기록. 가장 위험했던 부류는 예외를 던지지 않는 에러였다 — 화질이 조용히 깎이고, 313개가 실패해도 종료 코드는 0이었다. 아래는 그 12건과 조치다.

바로가기 · ① 조용한 실패 3건 · ② YouTube 접근 차단 3건 · ③ 대량 실행 견고성 3건 · ④ 속도 조절 도입 후 3건 · ⑤ 실행 환경 3건 · ⑥ 내 판단 오류 · ⑦ 미해결 · ⑧ 요약

이 문서가 다루는 범위. 코드 결함과 실행 중 실제로 부딪힌 오류만 다룬다. 설계 논의나 성능 수치는 제외했다. 관측한 현상과 코드에서 확인한 결함, 그리고 인과를 확정하지 못한 추정을 구분해 적었다 — 추정인 것은 본문에 그렇게 표시했다.

1. 조용한 실패 — 예외도 경고도 없이 잘못되던 것들

ERROR 1-1. 세로 영상 화질이 3.2배 손실되고 있었다

settings.ini 의 quality = 1080p 는 다음 선택자로 번역됐다.

bv*[height<=1080]+ba/b[height<=1080]

yt-dlp 의 height 는 세로 영상에서 긴 변이다. 1080×1920 쇼츠는 height 가 1920 이라 네이티브 포맷이 필터에서 탈락하고, 조건을 만족하는 608×1080 이 선택됐다. 픽셀 수로 3.16배 손실인데 종료 코드 0, 경고 없음이었다.

재현

$ yt-dlp -f "bv*[height<=1080]+ba/b[height<=1080]" --print "%(format_id)s %(resolution)s" <shorts>
788+251-2  608x1080      ← 깎임

$ yt-dlp -f "bv*+ba/b" -S "res:1080" --print "%(format_id)s %(resolution)s" <shorts>
399+251-2  1080x1920     ← 정상

수정

상한을 -f 필터에서 -S(format sort)로 옮겼다. yt-dlp 의 res 정렬 필드는 min(width, height) 이라, 짧은 변을 기준으로 가로·세로에 같은 규칙이 적용된다.

res:N 은 하드 상한이 아니라 정렬 선호다. 짧은 변 N 이하를 우선하되, 선택 가능한 포맷이 전부 N 을 초과하면 초과 포맷을 받는다. 예전 [height<=N] 필터는 그런 경우 아예 실패했으므로 이쪽이 더 안전하지만, "절대 N 을 넘지 않는다"는 보장은 아니다.

아래는 해당 화질대 포맷이 실제로 존재했던 영상에서 관측된 결과다.

대상원본-S res:1080 결과
세로 쇼츠1080×19201080×1920 (그대로)
가로 4K3840×21601920×1080 (캡)
가로 4K, res:7203840×21601280×720

compose_format_spec() 은 코덱/오디오 선호만 담고, 새 compose_format_sort() 가 상한을 맡는다. 주의: 상한이 -f 를 떠났으므로 사용자가 고른 화질을 반영하려면 compose_format_sort() 결과도 함께 넘겨야 한다. 엔진 호출에서 인자를 아예 생략하면 기본값 res:1080 이 적용되고(ytdlp.py:397), None 을 명시하면 -S 가 빠진다. 즉 "720p 로 설정했는데 1080p 가 받아지는" 형태로 어긋난다. cli / server(2곳) / gui / sidecar 5곳을 모두 갱신했다. 사용자가 raw -f 를 직접 준 경로는 그 선택자를 존중해 의도적으로 sort 를 붙이지 않는다.

검증

최종 다운로드 469개를 ffprobe 로 전수 확인(읽기 실패 0):

373  1080x1920   세로 — 네이티브 유지
 95  1920x1080   가로 — 정확히 캡
  1  1280x720    원본 최대가 720p 인 영상

짧은 변 1080 초과: 0개

ERROR 1-2. 313개가 실패해도 화면엔 성공 한 줄

쇼츠 350개 작업이 files=37 rc=0 으로 끝났다. 나머지 313개는 전부 실패했는데 아무 표시도 없었다. 원인은 세 가지가 겹친 것이다.

위치동작
cli.py _ACTIVITY_RE^\[ 로 시작하는 줄만 매치 → ERROR: / WARNING: 줄을 통째로 폐기
ytdlp.py--ignore-errors 가 항상 켜져 있어 항목 실패로 멈추지 않음
ytdlp.py 종료 처리파일을 하나라도 받았으면 non-zero exit 를 부분 성공으로 흡수

수정

_PROBLEM_RE 로 ERROR:/WARNING: 줄을 따로 모아 실행 종료 후 요약 출력. 종료 코드는 일부러 바꾸지 않았다 — sidecar/서버 등 기존 소비자의 계약을 유지하기 위해서다.

보관 한도는 입력 URL 단위로 200줄이다(cli.py:52, 491, 537). URL 마다 _StatusLine 이 새로 생기고 그 결과가 전체 목록에 누적되므로, URL 을 여러 개 주면 요약은 200줄을 넘을 수 있다. 엔진의 stderr_lines 버퍼에는 한도가 없다.

이 수정이 없었으면 봇 차단(2-2)을 아예 발견하지 못했을 것이다. 실제로 이 요약이 처음 재생목록 항목 경고/실패 586건 을 찍으면서 문제가 드러났다. 단, 586 은 매치된 로그 줄 수이지 실패한 영상 수가 아니다 — 영상 하나가 ERROR 와 WARNING 을 함께 남기기 때문이다. 실제 실패는 313개였다.

WARN 1-3. 완료된 작업 재실행이 거짓 실패로 보고됐다

--download-archive 를 쓰는 작업을 두 번째 실행하면 받을 게 없어 final_path 가 안 생기고, 엔진이 이를 Download completed but no filename reported 실패로 올렸다(exit 2).

수정

archive 스킵 로그를 센 뒤, 종료 코드가 0 또는 101 이고 final_path 가 없으며 스킵 로그가 하나 이상이면 already-archived 로 구분하고 CLI·서버가 성공으로 처리한다 (ytdlp.py:681-684, cli.py:525, server.py:328). 스킵 수를 전체 항목 수와 대조하지는 않으므로 엄밀한 "전량 스킵" 검증은 아니다. 정규식은 yt-dlp 의 두 가지 메시지 변형을 모두 잡아야 한다 — 재생목록 항목은 제목이 끼어든다(YoutubeDL.py:1645-1660 vs :1710, 이 프로젝트가 실제로 실행하는 yt-dlp 2026.06.09 기준. 엔진이 shutil.which("yt-dlp") 로 PATH 의 바이너리를 쓰므로 venv 사본과는 줄 번호가 다르다). 

[download] <id>: has already been recorded in the archive           ← URL 단계
[download] <id>: <제목> has already been recorded in the archive   ← 재생목록 항목

2. YouTube 접근 차단

ERROR 2-1. HTTP 403 — 메타데이터는 되는데 다운로드만 실패

ERROR: unable to download video data: HTTP Error 403: Forbidden

기본 클라이언트 설정에서 포맷 목록은 정상으로 나오는데 실제 미디어 fetch 만 죽었고, 클라이언트를 바꾸자 성공했다. yt-dlp 가 android_vr 을 골랐다는 것까지는 로그로 확인했다. 추정 SABR/PO-token 관련 문제를 의심했지만 (yt-dlp #12482), 이번 403 의 직접 원인은 확정하지 못했다 — 해당 이슈는 web 클라이언트가 SABR 로 적응형 포맷 URL 을 잃는 사례를 다루므로 이번 건과 같다고 단정할 수 없다.

수정

[network] player_client 설정과 --player-client 플래그를 추가해 --extractor-args youtube:player_client=<값> 로 전달한다. 값은 web_embedded,default — 순서가 중요하다.

default 를 뒤에 붙이는 것은 "앞 클라이언트로 받아 보고 실패하면 다음으로 넘어간다"가 아니다. yt-dlp 는 요청한 클라이언트들을 모두 처리해 포맷을 한데 모은 뒤 정렬로 고른다. 그래서 기본 클라이언트의 포맷이 선택돼 다시 403 이 날 여지가 남는다(미해결 참고). 실측에서는 web_embedded 를 앞에 둔 경우 403 나던 영상이 모두 성공했다.
player_client403 나던 영상
web_embedded1080×1920 성공
web_embedded,default1080×1920 성공 (채택 — 기본 클라이언트들도 추출 대상에 포함됨)
default,web_embedded403 실패

ERROR 2-2. 봇 감지 — 37개째부터 313개 전량 차단

ERROR: [youtube] <id>: Sign in to confirm you're not a bot.
       Use --cookies-from-browser or --cookies for the authentication.

쇼츠를 쉬지 않고 연속 요청하던 중 세션이 차단됐다. 같은 날 장편 영상 96개(항목당 처리 시간이 긴 쪽)는 실패 0건이었다. 추정 이 차이를 근거로 요청 빈도를 유력한 원인으로 봤다. URL 유형·세션·시간대 같은 변수를 분리해 검증하지는 않았다.

수정

엔진에 요청 간격 옵션이 아예 없었다. 세 개를 추가했다.

옵션역할
--sleep-requests메타데이터 요청 사이 대기
--sleep-interval / --max-sleep-interval영상 다운로드 사이 랜덤 대기

--sleep-requests 1 --sleep-interval 2 --max-sleep-interval 4 로 재개했을 때 코믹한영어 쇼츠 350개를 봇 차단 0건으로 완주했다. 다만 차단이 한 번 걸리면 즉시 풀리지는 않는다 — 이번엔 약 하루 뒤에 해제된 것을 단건 요청으로 확인하고 재개했다.

미해결로 남는 부분. 해시태그 쇼츠 작업에서는 하루 뒤 재개했음에도 21개만에 다시 차단됐다. 같은 날 이미 470개가량을 받은 뒤였다. 일일 총량에도 제한이 있는 것으로 보이나, 수치는 확인하지 못했다.

ERROR 2-3. 익명 쿠키가 오히려 다운로드를 깨뜨렸다

마지막 5개가 계속 Video unavailable 로 실패했다. 삭제된 영상인 줄 알았으나 availability 를 찍어 보니 public 이었다. 범인은 CLI 가 자동 감지해 넘기던 %APPDATA%\YCollector\cookies.txt 였다 — 로그인 세션이 아니라 오래된 익명 consent 쿠키다. 

--cookies <익명 cookies.txt>  →  ERROR: Video unavailable
쿠키 없이                      →  1080x1920 정상

조치

이번 작업은 존재하지 않는 경로를 --cookies 로 줘서 자동 감지를 무력화했다(CLI 가 파일이 아니면 경고 후 무시한다). 그 즉시 5개가 모두 성공해 350/350 이 됐다. TODO 깔끔한 --no-cookies 플래그는 아직 없다.

3. 대량 실행 견고성

ERROR 3-1. stderr 파이프 교착

엔진이 stdout 을 EOF 까지 다 읽은 뒤에야 stderr 를 읽고 있었다. --ignore-errors 로 도는 수백 개짜리 재생목록은 항목마다 진단을 뱉는다. stderr 파이프가 가득 차면 yt-dlp 는 stderr 쓰기에서, 부모는 stdout 읽기에서 서로 막힌다. 진행률이 멈춘 채 끝나지 않는다. (파이프 용량은 OS 가 정하며 이 환경에서 실측하지는 않았다.)

수정

전용 데몬 스레드가 stderr 를 즉시 드레인해 리스트에 모으고, on_log 디스패치는 예전처럼 download() 를 호출한 스레드가 이어서 한다 — 콜백이 두 스레드에서 동시에 불릴 일이 없다.

회수에는 한계가 있다. stdout EOF 후 리더를 최대 30초 기다리고, 그때까지 안 끝나면 "진단이 잘렸을 수 있다" 경고를 목록에 직접 끼워 넣는다. 종료 정리에서 5초를 더 기다리지만, 최초 디스패치 이후에 수집된 줄은 on_log 로 다시 보내지 않는다 (ytdlp.py:634, 642). 교착은 사라졌지만 극단적인 경우 마지막 몇 줄은 요약에서 빠질 수 있다.

WARN 3-2. CLI 에 재개 수단이 없었다

엔진은 download_archive 를 지원했지만 넘기는 건 server.py 뿐이었다. CLI 는 파일명이 같은지로만 건너뛰었는데, 이 방식은 항목마다 전체 추출을 수행한 뒤 판단하므로 재개가 느리고 제목이 바뀌면 같은 영상을 중복 저장한다.

수정

--download-archive PATH 추가. ID 를 미리 아는 항목은 개별 영상 추출 전에 걸러진다. 다만 채널·해시태그의 항목 열거 요청은 여전히 필요하므로 재개가 무조건 즉시는 아니다.

추출·미디어 다운로드 실패로 archive 에 기록되지 않은 항목은 재실행 시 다시 시도된다. 주의 다만 항상 켜져 있는 --ignore-errors 때문에 후처리 단계 오류는 archive 기록과 공존할 수 있다 — 그런 항목은 재실행해도 건너뛰므로 결과물을 따로 확인해야 한다. 출력 폴더마다 다른 파일을 쓰라는 경고를 도움말에 넣었다 — 폴더가 달라도 같은 archive 를 공유하면 받지도 않은 영상을 건너뛴다.

WARN 3-3. 강제 종료가 남긴 조각 파일

timeout 으로 죽이면 머지 전 조각이 남는다. 한 영상이 파일 3개로 보여 중복처럼 오인했다. 

<제목> [id].f251.webm   ← 오디오 조각
<제목> [id].f399.mp4    ← 비디오 조각
<제목> [id].mp4         ← 완성본

실제로는 완성본 327개 + 조각 54개 + .part 5개였다. 완성본만 세려면 .f<숫자>. 패턴을 제외해야 한다. 조각과 .part 는 정리했고, archive 의 중복 라인(410줄 → 327 unique)도 정리했다. 중복 라인 자체는 조회에 무해하다.

4. 속도 조절을 넣은 뒤 드러난 3건

WARN 4-1. max_sleep_interval 단독 지정이 통째로 무시됐다

처음엔 sleep_interval 이 참일 때만 max 를 내보냈다. yt-dlp 실측 결과는 이렇다.

--max-sleep-interval 3                      → yt-dlp: error: min sleep interval must be specified
--sleep-interval 0 --max-sleep-interval 3   → 정상 동작

수정: 둘 중 하나라도 설정되면 min 을 (없으면 0으로) 항상 함께 내보낸다.

WARN 4-2. nan / inf / 음수가 그대로 통과했다

float(raw) 만 쓰고 유한성을 확인하지 않았다. sleep_requests = nan 같은 설정이 Settings 에 들어가면 yt-dlp 뿐 아니라 웹 서버가 먼저 터진다 — Starlette 의 JSONResponse 는 allow_nan=False 라 /api/settings 응답 자체가 실패한다.

수정: _sleep_or_none() 을 두어 유한하고 음수가 아닌 값만 통과시키고, 나머지는 기본값을 유지한다.

WARN 4-3. sidecar / GUI 경로만 설정이 누락됐다

CLI 와 서버에는 전달했지만 sidecar 와 legacy GUI 는 빠져 있었다. 설정을 켜 놔도 그 경로로 도는 작업은 말없이 속도 조절 없이 돈다. player_client 도 sidecar 의 ready.defaults 에서 빠져 있었다. 수정: 두 경로 모두 전달하도록 보강.

5. 실행 환경에서 나온 에러

ERROR 5-1. 이모지 제목에서 UnicodeEncodeError

UnicodeEncodeError: 'cp949' codec can't encode character '\U0001f923'
                    in position 68: illegal multibyte sequence

제목에 🤣 가 들어간 파일을 진행 로그로 출력하다 배치 전체가 죽었다. 전사 자체와 무관한 곳에서 작업이 중단된 것이다. 수정: 출력 스트림을 utf-8 + errors="replace" 로 고정.

WARN 5-2. 백그라운드 작업이 반복 강제 종료

백그라운드 태스크가 세 번 종료됐고(다운로드 2회, 전사 1회) 당시 여유 메모리는 31.7GB 중 약 4GB 였다. 단일 독점 프로세스는 없었고 전체가 빠듯한 상태였다. 추정 메모리 부족이 직접 원인인지는 확인하지 못했다. 조치: 다운로드와 전사를 모두 포그라운드 청크로 전환. archive 와 skip-existing 덕에 완료된 산출물은 보존됐다 — 중단 시점에 진행 중이던 항목은 다시 받아야 했고, 실제로 조각 파일이 남았다(3-3).

NOTE 5-3. 셸 헤어로독이 백슬래시를 한 겹 먹었다

패치 스크립트를 heredoc 으로 넘길 때 "\\n" 이 실제 개행으로 변환되어 정규식 치환이 계속 실패했다. 조치: 패치 스크립트를 파일로 쓴 뒤 실행. 백슬래시가 필요한 곳은 chr(92) 로 조립.

6. 내 판단 오류 1건

403 이 해소됐다고 잘못 보고했다. 근거로 삼은 것이 --skip-download 실행이었는데, 그건 포맷 해석까지만 확인할 뿐 실제 미디어 fetch 를 하지 않는다. 실다운로드로 다시 확인하니 403 은 그대로였고, 그래서 player_client 우회를 도로 넣었다.

교훈: 다운로드 가능 여부는 반드시 실제 다운로드로 확인한다. 같은 함정이 하나 더 있다 — 이번 사례에서 작은 Range 요청(curl -r 0-999)이 206 을 돌려준 영상도 전체 다운로드는 403 으로 실패했다. 206 만으로 다운로드 성공을 판정할 수 없다.
